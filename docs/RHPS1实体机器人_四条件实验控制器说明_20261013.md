# RHPS1 实体机器人：四条件实验控制器

## 1. 目标

同一个 Control PC controller 支持四种实验条件，切换条件时不重新编译、不修改 YAML：

| 参数 | 输入延迟 | 共享自主 |
|---:|---:|---|
| 1 | 0.0 s | 关闭 |
| 2 | 0.0 s | 开启 |
| 3 | 1.5 s | 关闭 |
| 4 | 1.5 s | 开启 |

真机 controller 名称：

```text
ANAAvatarControllerRHPS1_experiment
```

原来的 `ANAAvatarControllerRHPS1_manual` 没有被替换，仍作为纯手动回退版本保留。
experiment 版本的运行时输入完全来自 Vive bridge，因此不再启动旧 Neuron mocap 插件；旧
retargeting state 在这里仅负责创建 mc_rtc hand/arm task。

## 2. 安全启动逻辑

Operator PC 发来的条件消息格式为：

```text
CONDITION:SESSION_ID
```

每次运行启动器都会生成新的 `SESSION_ID`。Control PC 收到新的 session 后会：

1. 把左右手、左右 arm 和头部 task 保持在当前目标；
2. 清空 1.5 秒输入历史，避免上一条件的样本泄漏到下一条件；
3. 关闭 tracking；
4. 重新等待左右手柄的 `menu` 确认；
5. 双侧确认且 tracker 数据齐全后，按原有 handover 逻辑平滑接管。

因此，仅启动脚本或发送参数不会让机器人运动。两只手柄也不必严格在同一毫秒按下，左右各确认
一次即可。现场切换条件前仍应让机器人和操作者停稳，并由急停人员确认。

## 3. Control PC 安装和启用

仓库仍作为 `mc-rtc-superbuild/extensions/` 下的 extension 构建。更新源码后，在 superbuild
根目录执行现场原有的项目 target；项目 target 名仍为：

```text
ANAAvatarControllerRHPS1_manual_project
```

这个 target 名只是 superbuild 项目名，现在会同时安装 manual 和 experiment 两个 controller。

在实际被 `hrpsys_mc_rtc.sh` 读取的 `mc_rtc.yaml` 中确认：

```yaml
MainRobot: RHPS1_sake2_sake2
Enabled: [ANAAvatarControllerRHPS1_experiment]
Timestep: 0.005
```

`MainRobot` 必须以现场已经修复并能与编码器数量匹配的 RobotModule 为准；如果实验室最终更换
RHPS1 模型名称，只统一修改真机配置，不需要复制四套 controller。

完成 `rhps1init`、`hrpsys_mc_rtc.sh`、`nocnoid22.py` 和传感器校准后，在 GUI 中选择并启动
`ANAAvatarControllerRHPS1_experiment`。在 Operator PC 发来条件前，它只保持当前姿态并等待。

## 4. Operator PC 一条命令选择条件

在本仓库的 `operator_pc` 目录运行：

```bash
cd ~/luyisi/github_upload/RHPS1_manual_vr_controller_20260820/operator_pc
./run_rhps1_experiment 1
```

把最后的数字换成 `2`、`3` 或 `4` 即可。脚本会同时：

- 加载 RHPS1 的 ROS 2/Zenoh 网络环境；
- 发布带唯一 session ID 的实验条件；
- 启动 Vive talker；
- 持续重发 transient-local 条件，允许 Control PC 稍后进入 experiment state。

看到 Control PC GUI 中的条件与 session 后，再分别按下左右手柄 `menu`。终止本轮时在该终端
按 `Ctrl+C`。启动器使用文件锁，防止两个实例同时发送互相冲突的条件。

## 5. 四种条件实际改变什么

延迟施加在 Vive hand/arm/waist 输入以及 HMD 旋转历史上：

- 条件 1/2：`input_delay = 0.0`；
- 条件 3/4：`input_delay = 1.5`。

机器人 ZED 相机到 HMD overlay 的画面不延迟。也就是说，操作者始终实时看到机器人视觉，但在
条件 3/4 中，手臂、腰部参考和机器人头部会响应 1.5 秒前的 Vive 姿态。

辅助使用独立硬门控：

- 条件 1/3：左右 SharedAutonomy task 权重归零，手动 retargeting 权重恢复；
- 条件 2/4：门控打开，但只有 tracking 已启动、意图数据有效且 alpha 大于零时才介入。

四种条件都可以接收 Cornel 的 `/goal_beliefs` 与 `/left_goal_beliefs`，所以无辅助条件仍能记录
同一套 landmark、belief、confidence 和 alpha，而不会把辅助写进机器人动作。

## 6. 意图识别的独立进程

本启动器只负责实验条件和 Vive 设备输入。Cornel/CHMM 感知仍是 Operator PC 上的独立进程，
需要 ZED ROS 2 RGB、depth、camera info，以及 controller 发布的机器人相机/手位置。当前入口为：

```bash
cd ~/luyisi
./run_cornel_rhps1_intent_zed_ros
```

在 1/3 中可以保持它运行用于公平记录；在 2/4 中它还为辅助提供 goal belief 和目标位置。
如果该进程未运行、消息超时或目标坐标无效，experiment controller 会退回纯手动控制，条件 2/4
不会凭空生成辅助。

## 7. 日志核对

mc_rtc 日志增加以下字段：

```text
ANA::ViveHandBridgeExperiment_experiment_condition
ANA::ViveHandBridgeExperiment_experiment_condition-name
ANA::ViveHandBridgeExperiment_experiment_session-id
ANA::ViveHandBridgeExperiment_experiment_input-delay-s
ANA::ViveHandBridgeExperiment_experiment_assistance-enabled
ANA::ViveHandBridgeExperiment_experiment_tracking-started
```

左右 SharedAutonomy 还记录：

```text
*_experiment_experiment-gate-open
*_experiment_data-ready
*_experiment_assistance-requested
*_experiment_assistance-active
*_experiment_effective-alpha
*_experiment_active-duration-s
*_experiment_active-episode-count
*_experiment_current-goal
```

这样每份日志都能回答：本轮属于哪个条件和 session、何时开始 tracking、辅助门是否打开、辅助是否
实际生效、持续多久以及对应哪个目标。

## 8. 尚未替代现场验证的部分

本版本已经在 Operator PC 完成 C++ 编译、YAML 生成和脚本静态检查，但不能替代以下真机验证：

1. `RHPS1_sake2_sake2` 与实体编码器数量必须匹配；
2. 条件消息和 Vive 消息必须能通过现场 Zenoh router 到达 Control PC；
3. 真实 ZED 检测得到的目标位置必须位于 controller 接受的机器人坐标系；
4. 条件 2/4 第一次只能在低风险物体、急停人员就位时验证；
5. 不应在同一轮同时首次调试 Sake2、视觉、意图识别和辅助动作。
