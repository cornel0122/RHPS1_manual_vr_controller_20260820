# RHPS1 实体机器人：最小手动 VR 控制器安装摘要

## 1. 本阶段的唯一目标

在 RHPS1 实体机器人上验证最基础的 Vive 手动遥操作链：

```text
Operator PC 的 Vive 设备
  -> ROS 2 controller/tracker/HMD 消息
  -> Control PC 的 ViveHandBridge/ViveHeadBridge
  -> ANA retargeting tasks
  -> mc_rtc QP
  -> RHPS1
```

本阶段不包含：

- 输入延迟（固定为 0 秒）；
- Guillaume/Cornel 意图识别；
- 共享自主；
- YOLO、CHMM、goal belief；
- MuJoCo、仿真物体真值、磁力抓取；
- 自动倒水等 secondary-stage 技能；
- 行走控制实验。

## 2. 操作者实际能控制什么

- 左右 controller 的位置和姿态 -> RHPS1 左右手 `TransformTask`；
- 左右大臂 tracker 的方向 -> 左右肩/手臂姿态 task；
- 腰部 tracker -> 人体坐标参考系；
- HMD 姿态 -> RHPS1 `HEAD_P`、`HEAD_Y`；
- controller 的 grip -> 左右夹具开闭；
- 双手 menu 首次同时确认 -> 允许 Vive 正式接管，并建立头部/人体参考；
- trigger 的“已抓住”通知在本阶段没有消费者，不影响手动控制。

当前输入参数：

```yaml
input_delay: 0
use_linear_velocity_feedforward: true
linear_velocity_gain: 1.0
use_angular_velocity_feedforward: false
use_waist_reference: true
require_initial_two_hand_reset: true
control_grippers: true
```

手的最终目标由位置、姿态以及线速度前馈共同形成；QP 再根据 RHPS1 的关节、碰撞和任务约束求出关节命令。操作者不直接发送关节角。

## 3. 四台电脑中的部署位置

### Operator PC（当前电脑）

运行：

- SteamVR；
- ViveSimpleInterface 的 `talker`；
- 以后需要时运行真实机器人相机的 HMD overlay。

不运行 mc_rtc QP，不直接控制 EtherCAT。

### Control PC（RHPS1 内部）

安装并运行：

- `ANAAvatarControllerRHPS1`；
- `ViveHandBridge`、`ViveHeadBridge`；
- `vr_interface_msgs`；
- 机器人原有的 mc_rtc、mc_openrtm、mc_rhps1、稳定器和安全链。

### Terminal PC

用于 SSH、`bodystat`、`io-main.log`、`nocnoid22.py` 和 mc_rtc GUI。

### Vision PC

本阶段不需要。ZED、YOLO 和 Cornel 程序都可以暂不启动。

## 4. 需要带到 Control PC 的源码

### 必须复制

1. 控制器源码：

```text
guillaume_code/mc_ana_avatar_controller_rhps1_fusion/
```

2. ROS 2 自定义消息包：

```text
ViveSimpleInterface-main/ros/vr_interface_msgs/
```

Control PC 不需要复制依赖 OpenVR 的 `vr_interface_node/talker`，因为 talker 留在 Operator PC。

### 不要复制或安装

- `install_ana_rhps1_fusion` 中本机编译的 `.so`；
- `run_ana_rhps1_mujoco_*`；
- `rhps1_mj_description` 和 Fixed MuJoCo RobotModule；
- MuJoCo 场景、桌子、物体和 adhesion 修改；
- Cornel/Walid Python 项目；
- AssistedTeleoperationPlugin；
- 本机的 `~/.config/mc_rtc/mc_mujoco`。

二进制必须在 Control PC 上依据其 mc_rtc/编译器/ROS ABI 重新构建。

## 5. 构建依赖

当前控制器 CMake 会查找：

- mc_rtc（必须带 ROS 支持）；
- mc_rhps1/真实 RHPS1 RobotModule（运行时）；
- lipm_walking_controller；
- mc_neuron_mocap_plugin；
- ForceConstrainedTransformTask；
- ROS 1 compatibility：roscpp、geometry_msgs；
- ROS 2：rclcpp、geometry_msgs、std_msgs；
- vr_interface_msgs。

前五项大概率已存在于 Control PC 的 RHPS1 环境，但必须由实验室同事确认版本和安装前缀，不要自行替换机器人已有的 mc_rtc。

## 6. 推荐安装顺序

### 第一步：只记录环境

```bash
uname -a
echo "$ROS_DISTRO"
echo "$ROS_DOMAIN_ID"
echo "$RMW_IMPLEMENTATION"
pkg-config --modversion mc_rtc
```

同时询问实验室同事：

- 应使用哪个用户和 superbuild；
- RHPS1 RobotModule 的准确名称；
- `hrpsys_mc_rtc.sh` 读取哪个 `mc_rtc.yaml`；
- controller 应安装到哪个前缀；
- Operator PC 与 Control PC 使用 DDS 直连还是 Zenoh/router。

### 第二步：单独构建消息包

把 `vr_interface_msgs` 放入 Control PC 的 ROS 2 colcon workspace：

```bash
source /opt/ros/humble/setup.bash
cd <control-pc-ros2-workspace>
colcon build --packages-select vr_interface_msgs
source install/setup.bash
```

实际 ROS 发行版以 Control PC 为准；若不是 Humble，必须重新核对兼容性。

### 第三步：构建控制器源码

首选把控制器作为现有 `mc-rtc-superbuild` 的独立 extension 构建。不要覆盖已有演示用户的 controller。

若实验室同事确认可以使用独立安装前缀，等价的 CMake 结构是：

```bash
source /opt/ros/<实际发行版>/setup.bash
source <control-pc-ros2-workspace>/install/setup.bash

cmake -S <mc_ana_avatar_controller_rhps1_fusion> \
      -B <build-directory> \
      -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_INSTALL_PREFIX=<private-install-prefix> \
      -DINSTALL_DOCUMENTATION=OFF
cmake --build <build-directory> -j
cmake --install <build-directory>
```

这些命令只是结构示例；现场应优先采用 RHPS1 superbuild 的安装方式。

### 第四步：只验证加载

确认安装结果中至少存在：

```text
lib/mc_controller/ANAAvatarControllerRHPS1.so
lib/mc_controller/etc/ANAAvatarControllerRHPS1_manual.yaml
lib/mc_controller/ANAAvatarControllerRHPS1_manual/rhps1.yaml
lib/mc_controller/ANAAvatarControllerRHPS1/states/ViveHandBridge.so
lib/mc_controller/ANAAvatarControllerRHPS1/states/ViveHeadBridge.so
```

让 mc_rtc 能发现 controller，但暂时不要启动机器人动作。

## 7. 真机配置原则

真机应使用真实、非 Fixed、非 MuJoCo RobotModule：

```yaml
MainRobot: <现场确认的 RHPS1 RobotModule 名称>
Enabled: [ANAAvatarControllerRHPS1_manual]
Timestep: 0.002
```

不要使用：

```yaml
MainRobot: RHPS1_sake2_sake2_Fixed_MuJoCo
Enabled: [ANAAvatarControllerRHPS1_none]
```

不要加载 `AssistedTeleoperationPlugin`。纯手动 FSM 本身不创建意图识别、共享自主或共享自主 UI 状态。

## 8. 真机纯手动 FSM 与剩余风险

### 8.1 已跳过仿真准备轨迹

`ANAAvatarControllerRHPS1_manual` 从 LIPM 初始站立状态进入 `ANA::ManualDemo`，随后直接进入 `Avatar::Retargetting::Manual`。它不会进入 `PrepareRHPS1ForVR`，也不会使用仿真桌面绝对坐标。

Vive bridge 在启动时把手和 arm task 固定到当前机器人姿态。左右手柄均确认前持续保持；确认后按配置的 2 秒 handover 平滑接管。

不要在真机配置中误选 `ANAAvatarControllerRHPS1` 或 `ANAAvatarControllerRHPS1_none`，这两个兼容变体仍保留旧实验流程。

### 8.2 已从运行链移除共享自主

`Avatar::Retargetting::Manual` 只包含：

```text
ROSInputState
RetargetingReference
左右 hand/arm retargeting task
ViveHandBridgeManual
ViveHeadBridge
```

`ViveHandBridgeManual` 还会关闭 MuJoCo adhesion 和旧 Unity 兼容话题。

### 8.3 肩部 local-minimum workaround 尚未真机验证

当前左右手配置启用了柔和的 `SHOULDER_P` posture override（weight 50、stiffness 2）。仿真中效果较好，但真机第一次测试前应由工程师决定是否启用，并监视肩部目标与速度。

### 8.4 现场确认 LIPM 足部中点配置

本地 Fixed MuJoCo 加载测试中，LIPM 曾打印 `Invalid X_0_mid("external")`。控制器随后仍完成初始化，但这一参数必须在 Control PC 上使用真实 RHPS1 RobotModule 再确认。确认前只做编译、controller 发现和日志检查，不开始真机运动。

## 9. ROS 2 跨电脑通信验证

Operator PC 启动：

```bash
cd ~/luyisi
./run_vive_talker
```

Control PC 在任何机器人运动之前验证：

```bash
ros2 topic echo /controller_1 --once
ros2 topic echo /controller_2 --once
ros2 topic echo /tracker_1 --once
ros2 topic echo /tracker_2 --once
ros2 topic echo /tracker_3 --once
ros2 topic echo /hmd --once
```

如果 Control PC 看不到话题，不要启动 mc control。优先检查：

- ROS_DOMAIN_ID；
- RMW_IMPLEMENTATION；
- ROS_LOCALHOST_ONLY 必须为 0；
- 消息包版本；
- DDS discovery/防火墙/Zenoh 配置；
- `sudo -E` 是否保留 ROS 环境。

## 10. 第一次现场验证等级

1. **安装检查**：controller 能被发现，无 missing library、ABI、message type 错误。
2. **加载检查**：只加载 controller，不 Start MC Control。
3. **输入检查**：Control PC 能看到 Vive 话题和正确 serial，机器人不接管。
4. **静止接管**：双手 menu 未确认时，目标不能跳变。
5. **单自由度小幅运动**：一次只测一个手的位置方向。
6. **姿态与 arm tracker**：随后再测手姿态和肩部方向。
7. **夹具**：手臂静止时单独测试开闭。
8. **头部**：最后测试 HEAD_P/HEAD_Y。

全程应有人操作急停，并同时监视：

```bash
bodystat
tail -f /var/log/io-main.log
```

发现目标跳变、肩部旋转异常、关节接近限位、脚底压力异常或机身摇晃时立即停止。

## 11. 现场常用启动流程（由负责人确认后执行）

Control PC/Terminal PC 现有 RHPS1 流程线索为：

```bash
bodystat
tail -f /var/log/io-main.log
rhps1
sudo -E ./hrpsys_mc_rtc.sh
rhps1
./nocnoid22.py
ros2 launch mc_rtc_ticker display.launch
```

Operator PC 额外运行 `run_vive_talker`。本阶段不运行 Vision PC 的 `zed_stream` 和 Walid/Cornel `main.py`。

`Start MC Control` 必须在安装、RobotModule、FSM、准备姿态和急停人员全部确认后才能按下。

## 12. 当前结论

我们已经具备：

- 在 Operator PC 稳定发布 Vive ROS 2 数据的程序；
- 在 MuJoCo 中验证过的 RHPS1 手、arm、waist、head 和夹具映射；
- Control PC 所需的 controller 源码和消息定义；
- 0 秒延迟、线速度前馈开启、角速度前馈关闭的基础配置。

真机最小 FSM 已建立，并已从运行链移除仿真准备轨迹和共享自主。尚未完成的是现场 RobotModule/稳定器/夹具接口核对，以及肩部 override 的真机确认。因此第一次安装仍应以编译、controller 发现和 ROS 2 通信为首要目标；实际运动必须按验证等级逐步进行。
